# 기존 Leaks 기록 재확인

2026-11-01. 새 녹화 없이 보관된 memory-hls-leaks-part1~4.trace를 확인했다. 원본 trace를 덮어쓰거나 삭제하지 않았다.

## 확인 결과

part4를 Instruments에서 정상적으로 열었다. 이 파일에는 Run 3, 4, 5, 6이 있으며 각 Run의 전체 시간축에서 Leaks의 초록색 체크 표식과 빈 Leaked Object 목록을 직접 확인했다. Detail Filter는 비어 있었다. 따라서 기존 ‘누수 결과 행 0’이 검사 표식 자체가 없는 기록은 아니라는 점을 보강했다.

이 표는 UI 직접 관찰 기록이다. 스크린샷을 저장소에 보존한 증빙이나 검사별 상태 코드를 내보낸 결과는 아니다. 시간축 끝의 표식이 경계에 걸릴 수 있어 정확한 성공 검사 횟수를 눈대중으로 집계하지 않았다. Snapshots 팝오버는 자동 검사 설정이지 과거 검사별 결과 목록이므로 이를 성공 횟수의 근거로 쓰지 않았다. 설정 변경이나 새 Snapshot 실행은 하지 않았다.

## 중복 기록 대조

각 파일의 instrument_data 아래 ZIP 멤버 중 XRLeaksRun 아카이브만 읽었다. 압축 해제 내용의 SHA-256으로 비교하면 part1~4의 총 10개 아카이브는 고유 4개다. 모든 아카이브에 XRLeakSnapshotInfo 클래스가 존재한다. 클래스 이름은 직렬화 시 공유되므로 문자열 출현 횟수를 검사 횟수로 세지 않았다.

[archive-manifest.json](archive-manifest.json)에 상대 경로·멤버 이름·길이·해시를 기록했다. 10개/고유 4개/스냅샷 클래스 존재 assertion을 통과했다. 이전 집계의 중복 제거와 일치한다.

## 판정 범위

- 기존 분할 측정의 검사 실행 및 누수 미검출에 대한 UI 근거를 추가 확보했다. 이 항목만 확인하기 위해 새 trace를 받을 필요는 없다.
- 내부 아카이브는 NSArchiver typedstream 형식이다. 이번 작업에서 검사별 상태 필드를 해독하지 않았으므로 정확한 성공/실패 검사 수는 미집계다.
- 누수 미검출은 모든 누수가 없다는 증명이 아니다. 동일 프로세스의 0/5/10/15/20회 잔존량 추세, 실제 표시 프레임 간격 및 C4 목표 판정은 별도로 남는다.
- 과거 측정 바이너리의 결과이며 최신 앱 코드의 메모리 성능을 재측정한 것이 아니다. 앱 코드 변경·앱 테스트 재실행은 없었다.
