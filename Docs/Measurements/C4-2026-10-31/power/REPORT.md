표는 interval과 구간이 겹치는 시간으로 가중 평균했다. 서브시스템별 별도 행과 sentinel을 구분하고 유효 관측만 사용했다. 각 구간의 모든 지표 관측 시간은 구간 길이와 0.001초 이내로 일치한다. 단순 행 평균으로 빈 GPU/CPU 값을 0 처리하지 않았다. summary.json에 정확한 값·최대·coverage, analyze.py에 계산 코드를 보존했다.

지표는 Power Impact 상대 점수이며 W, J, CPU 사용률, 배터리 %가 아니다. 서브시스템 합계를 배터리 소모율로 환산하지 않는다. 앱 재생 시작/종료 로그는 export되지 않아 구간은 안내한 30/150초 계획에 따른 추정이다. 실제 화면 전환은 표로 확정하지 않는다. 157초 CPU/GPU 변화가 있어 150~180초에는 화면 종료·복귀 처리가 섞였을 수 있다. 이 때문에 후반 160~180초를 보조 구간으로 별도 제시했다.

## 관측 해석

- 예정 재생 구간에서 CPU 평균은 0.090→0.426, 화면 영향은 1.448→2.108로 상승했다. CPU 최대 11.0은 약 32.04초 시작 표본으로 재생 시작 부근에 있다. 장시간 높은 CPU 점수가 계속 유지된다는 패턴은 이 평균과 표본에서 확인되지 않는다. 단일 기록으로 에너지 최적화 완료/문제 없음은 판정하지 않는다.
- 네트워크 수신은 대부분 34.06~50.05초에 집중된다. 전체 Wi-Fi 수신 40,707,573B(약 40.7MB), 송신 99,290B이며 셀룰러 송수신 0B다. 스트리밍의 선행 버퍼링과 일치할 수 있지만 로그가 없으므로 캐시/요청 원인을 확정하지 않는다. 네트워크 0으로 표시되는 후반을 재생 중단으로 해석하지 않는다.
- 예정 복귀 150~180초 전체 CPU 평균이 재생 평균보다 높지만 157초의 변화가 포함된다. 후반 160~180초에는 CPU 0.205, GPU/네트워크 0으로 내려간다. 재생 종료 뒤 지속적인 GPU/네트워크 부하 증거는 없지만 CPU는 초기 대기와 동일하지 않으므로 완전한 idle 복귀를 증명하지 않는다.
- 화면 영향 차이에는 밝기 54~59% 변동과 콘텐츠·화면 전환이 함께 작용할 수 있다. 변화 전부를 플레이어의 비용이라고 단정하지 않는다.

## C4 판정과 추가 측정 필요 여부

Wi-Fi에서 HLS 사용 시 앱별 전력 영향 측정 증빙은 확보했다. 이 목적만으로 다시 측정할 필요는 없다. 기기 전체 배터리 소모율/셀룰러 전력 영향/성능 목표 PASS는 아직 미판정이다.

절대 배터리 소모율이 과제에서 필요할 때만 충전 케이블·MagSafe를 제거하고 무선 연결 또는 기기 자체 Power Trace로 별도 측정한다. 셀룰러 비교가 필요하면 네트워크를 실제 셀룰러로 유지해야 한다. 동일 기기/밝기/열 상태/동작 구간을 맞춰야 하며 지금 파일을 폐기하거나 재빌드할 필요는 없다.
