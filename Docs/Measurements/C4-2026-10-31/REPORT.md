[도구 사용법](../../FRAME_SUMMARY.md)에 따라 manifest의 각 입력 TOC/events 해시와 Run을 확인하고 window_start_s/window_end_s를 --start/--end로 지정하면 각 JSON을 재생성할 수 있다. XML은 원래 로컬 exports를 사용한다. 입력 파일 해시는 동일 파일 여부 확인용이며 기기 조건이나 바이너리 커밋을 증명하지 않는다.

검증: 7개 집계 모두 available; staged1의 Hitch 3개·합계 133.361332ms 및 최대 Update 90.263875ms가 기존 분석과 일치. frame/runtime/TTFF 도구 단위 테스트 총 18개 통과. 문서/집계 산출물 변경이므로 Xcode 빌드와 실기기 재측정은 반복하지 않았다.

## 2026-11-03 반복 재생 후 메모리 측정

앱은 같은 프로세스의 물리 메모리 사용량(`TASK_VM_INFO.phys_footprint`)을 MiB로 표시한다. Allocations의 생존 객체 바이트와는 집계 범위가 달라 별도 표로 기록한다.

1. Xcode에서 `StreamLab-Firebase`와 iPhone을 선택한다. Edit Scheme → Run → Info에서 `FirebaseRelease`를 선택하고 Debug executable을 해제한다. Run → Arguments에 `--measure-hls-memory`를 켠 뒤 ⌘R로 실행한다.
2. 같은 프로필에서 ‘Apple HLS 연결 확인용 샘플’의 상세를 열고 10초 대기한다. ‘HLS 메모리 측정 시작’을 눌러 기준값을 기록한다.
3. 상세의 ‘영상 재생’ → 첫 화면이 움직인 뒤 5초 재생 → 닫기를 같은 상세에서 20회 반복한다. 각 5번째 종료 뒤 2초 후 수치가 표시되면 다음 회차를 시작한다. 재생 상태에 도달하기 전에 닫은 회차는 집계에서 빠진다.
4. 0·5·10·15·20회 수치가 모두 보이는 화면을 캡처한다. 빌드 커밋, 기기/iOS, 네트워크 종류를 함께 기록하고 실행 인수를 해제한다. 최종값과 기준값 차이, 5회 단위 변화량을 비교한다. 증가량만으로 누수나 과제 합격 여부를 판정할 수 없다.

사용자 제공 캡처에서 ‘Apple HLS 연결 확인용 샘플’ 20/20회와 다섯 측정점을 확인했다. 사용자 보고 환경은 iPhone 15 Pro, iOS 26.6.1, Wi-Fi다.

| 재생 후 닫기 | 메모리(MiB) | 직전 측정 대비(MiB) |
|---:|---:|---:|
| 0회 | 28.92 | — |
| 5회 | 36.86 | +7.94 |
| 10회 | 36.75 | -0.11 |
| 15회 | 36.64 | -0.11 |

20회 시점은 시작보다 7.83 MiB 높다. 처음 5회 동안 7.94 MiB 증가했고, 5회에서 20회까지는 0.11 MiB 감소했다. 이 실행의 후반 측정점에서는 반복에 따른 지속 증가가 보이지 않았다. 첫 증가의 원인이나 개별 객체의 누수 여부는 이 수치만으로 특정할 수 없다.

## 2026-11-03 홈 스크롤 실제 표시 간격

**과제 원문 대조.** 제공된 `Netflix_iOS_과제.docx`의 C4 피드 스크롤 제출 항목은 2,000개 fixture에서 Instruments 프레임 타임 p50/p95를 구하는 것이다. 기기 조건과 전후 개선 근거도 요구한다. 이 항목에는 고정 FPS나 p95 상한이 없다. 비교 버전 A(`340055c`)·B(`a86ea40`)의 번들 `catalog.json`을 각각 읽어 고유 작품 ID 2,000개를 확인했다. 데이터셋 전체를 홈에서 순회했다는 뜻은 아니다.

| iPhone 15 Pro · iOS 26.6.1 | Run | 분석 창(초) | 열 상태 | 연속 표시 간격 수 | p50(ms) | p95(ms) |
|---|---:|---:|---|---:|---:|---:|
| 10월 31일 홈 | 1 | 15–35.876725 | Nominal | 981 | 12.503 | 25.005 |
| 변경 전 A1 | 2 | 15–40 | Nominal | 1,108 | 12.503 | 20.838 |
| 변경 전 A2 | 2 | 15–40 | Fair | 912 | 12.503 | 33.340 |
| 변경 후 B1 | 2 | 15–40 | Serious | 862 | 12.503 | 33.340 |
| 변경 후 B2 | 1 | 15–40 | Nominal | 993 | 12.503 | 41.675 |

**해석.** 10월 31일 기록에서 앱이 갱신한 새 프레임의 첫 표시 시각은 15.565초, 마지막은 30.172초다. 이 982개 시각의 차이 981개를 집계했다. 이 구간에는 앞서 분류한 Hitch 3건(합계 25.005ms)이 있다. p95와 Hitch 합계가 반올림하면 같지만 서로 다른 지표다. 기존 App Update p95 7.557ms는 프레임을 준비하는 앱 작업 시간이다. 측정 창에는 손가락을 떼거나 방향을 바꾸는 시간도 포함된다. 466.763ms인 최장 간격을 단독으로 스크롤 멈춤이라고 분류하지 않았다.

**전후 비교.** 10월 27일 A/B는 사용자 확인 기준 녹화 15초부터 스크롤했고, 공통 15~40초만 비교했다. 중앙값은 네 회차 모두 12.503ms였다. 열 상태가 Nominal인 A1과 B2에서도 p95는 20.838ms에서 41.675ms로 늘었다. A2는 B2 이후 A로 재빌드해 측정했고 B1은 Serious였다. 손동작 속도·왕복 간 정지 시간이 달라 B 변경이 원인이거나 성능 개선에 성공했다고 판단할 수 없다. 10월 31일 측정은 창과 빌드가 달라 A/B와 합산하지 않았다. 이 값은 과거 시뮬레이션 데이터셋을 쓰는 앱의 실기기 관측이며 최신 Firebase 빌드의 실측으로 간주하지 않는다.

**계산 및 검산.** 각 Run의 최상위 StreamLab App Update를 display·swap ID·surface ID로 Frame Lifetimes와 연결했다. 실제 lifetime의 끝인 start + duration을 표시 시각으로 삼았다. 같은 시각을 한 번만 세고 두 끝점이 모두 측정 창 안인 인접 시각의 차이에 nearest-rank를 적용했다. 앱 업데이트에 귀속되지 않는 시스템 합성과 무변화 화면 재주사는 제외했다. Apple은 실제 frame lifetime의 끝을 프레임이 화면에 교체되는 vsync로 정의한다. [Apple의 frame lifetime 설명](https://developer.apple.com/documentation/xcode/understanding-hitches-in-your-app)

10월 31일 Run의 직접 swap 테이블에는 7행만 있었다. 기록 시작 직전 프레임을 제외하고 lifetime과 겹치는 6개 swap에서 두 시각의 차이는 최대 1ns였다. 이 교차 검산은 초반 구간에 한정된다. 10월 31일 기존 보관 export로도 같은 981개 및 p50/p95를 재현했다. [Run별 구간·수치·입력 해시](display-intervals.json) · [재집계 스크립트](../../../scripts/summarize-displayed-frames.py)

재현 예시(저장한 trace 경로를 지정):

```sh
xcrun xctrace export --input "$trace" --toc --output toc.xml
xcrun xctrace export --input "$trace" --xpath '/trace-toc/run[@number="1"]/data/table[@schema="hitches-updates" or @schema="hitches-frame-lifetimes"]' --output frames.xml
python3 scripts/summarize-displayed-frames.py toc.xml frames.xml --run 1 --start 15 --end 35.876725
```

A/B는 표의 Run 번호를 XPath와 집계 명령 양쪽에 적용하고 종료 시각은 40초로 둔다. 10월 31일 원본 재분석에서는 직접 swap 대조를 위해 같은 XML에 display-surface-swap과 display-events-interval 테이블도 함께 내보냈다.
